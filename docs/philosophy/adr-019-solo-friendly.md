# Solo_Friendly

**Status**: Accepted. 2026-04-24 결정의 상위 기준과 시간 예산을 유지해요. 2026-11-24 개정에서는 현재 백엔드 운영에 맞춰 관리형 서비스·직접 운영의 비교 기준과 blue-green 배포의 위치를 정리했어요.

## 결론부터

이 템플릿의 모든 아키텍처·도구·운영 결정은 **솔로 한 사람이 감당할 수 있는가**를 기준으로 판단해요. 지금 필요한 효과와 개발·유지·장애 대응에 드는 시간을 함께 비교해요. 기술의 유행이나 미래 확장 가능성만으로 현재의 복잡도를 늘리지는 않아요.

관리형 서비스와 직접 운영은 비용·시간·복구 책임을 비교해서 선택해요. Flutter의 Sentry·PostHog 연동과 백엔드 홈서버의 MinIO·관측 스택을 함께 사용하는 것도 이 기준에 따른 선택이에요. 로컬 개발, 필요한 Kit 선택, 명시적인 자격 관리와 검증을 유지해요.

99.99% 가용성 SLA 보장, 멀티 리전, Kubernetes·서비스 메시, 마이크로서비스 분산 추적은 기본 목표가 아니에요. 백엔드의 Kamal blue-green 배포는 채택한 방식이며, 무중단이나 가용성을 보장한다는 약속과는 구분해요.

## 왜 이런 고민이 시작됐나?

기술 선택에는 팀 규모, 트래픽, 배포 빈도, 복구 요구 같은 전제가 있어요. 여러 팀의 독립 배포를 위한 구조가 한 사람이 여러 앱을 운영하는 상황에도 그대로 맞는 것은 아니에요.

반대로 단순함만을 이유로 공통 계약과 검증을 없애면 앱마다 비슷한 코드를 복사하고 수정해야 해요. 이 템플릿은 필요한 공통 기반은 재사용하면서, 앱에 필요하지 않은 기능과 운영 대상은 줄이려는 구조예요.

판단할 때는 다음 요구가 함께 작용해요.

- **검증된 도구 활용**: 기존 기술의 장점을 참고하되 적용 전제가 현재 앱과 맞는지 확인해요.
- **현재의 제약**: 개발자의 시간·주의력·지출 범위 안에서 관리할 수 있어야 해요.
- **향후 변경 가능성**: 성장과 팀 확대를 확정하지 않되, 경계와 교체 지점은 이해할 수 있게 유지해요.
- **출시와 유지의 균형**: 첫 출시만 빠르게 끝내는 것과 이후 여러 앱을 계속 관리하는 것을 함께 고려해요.

> 한 사람이 앱을 만들고 유지하는 데 필요한 구조와 운영 범위는 어디까지인가요?

## 고민했던 대안들

<a id="option-1--업계-표준-그대로-따르기"></a>

### Option 1 — 업계 표준 그대로 따르기

마이크로서비스, 여러 아키텍처 계층, 분산 추적, 높은 가용성 목표를 기본값으로 도입하는 방식이에요. 팀별 책임과 배포 단위를 나눠야 하는 환경에서는 장점이 있어요.

현재 요구를 확인하지 않은 채 모두 도입하면 설정·검증·운영 대상이 늘어나요. 그래서 이 방식을 기본값으로 채택하지 않아요. 실제 요구가 생기면 효과와 유지 비용을 따로 검토해요.

<a id="option-2-대충-하자-로-완전히-기본적만"></a>
<a id="option-2--대충-하자-로-완전히-기본적만"></a>

### Option 2 — 공통 구조 없이 화면별로 구현하기

화면마다 HTTP 호출과 상태를 직접 관리하고, 공통 계약이나 모듈 경계를 두지 않는 방식이에요. 처음 시작할 때 필요한 구조는 적지만 여러 앱에서 공통 변경을 전파하고 검증하기 어려워져요.

초기 구조를 줄이더라도 유지에 필요한 경계까지 없애지는 않아요. 공통 자산을 재사용하는 템플릿의 목적과 맞지 않아 채택하지 않아요.

<a id="option-3-솔로-감당-가능성-을-명시적-기준으로-채택-채택"></a>
<a id="option-3--솔로-감당-가능성-을-명시적-기준으로-채택--채택"></a>

### Option 3 — 솔로 감당 가능성을 명시적 기준으로 채택 ★ (채택)

각 도구와 구조가 현재 요구를 해결하는지, 한 사람이 이후에도 책임질 수 있는지 확인해요. 필요한 모듈 경계·계약·검증은 유지하고, 아직 필요하지 않은 계층과 운영 체계는 도입을 미뤄요.

판단 근거와 비목표를 기록하고, 예상보다 운영 부담이 커지면 재검토해요. 이 기준은 기술을 무조건 줄이는 규칙이 아니라 필요한 초기 투자와 반복 비용을 비교하는 기준이에요.

## 결정

### 운영 결정의 판단 기준

모든 결정에 다음 질문을 적용해요.

1. 평소 점검·업데이트·자격 교체를 혼자 계속 수행할 수 있나요?
2. 작업 시간 밖에 장애가 발생해도 상태를 확인하고 복구할 절차를 이해할 수 있나요?
3. 앱이 10개로 늘어나는 경우에도 같은 수작업을 앱마다 반복하지 않을 수 있나요?
4. 새 구성의 기본 설정과 핵심 동작을 1시간 안에 이해하는 것을 목표로 삼을 수 있나요?

마지막 두 항목은 규모를 가정한 검토와 시간 목표예요. 실제 운영 실적을 뜻하지 않아요. 목표를 넘는다면 더 단순한 대안과 이후에 줄어들 작업을 비교하고, 현재 구성이 필요한 이유를 남겨요.

### 비목표 (Non-Goals) 명시

| 비목표 | 현재 범위와 이유 |
|---|---|
| 99.99% 고가용성 SLA 보장 | 이 템플릿은 해당 가용성을 측정·보증하는 운영 체계를 제공하지 않아요. |
| 멀티 리전 배포 | 기본 구성에 리전 간 복제·장애 전환을 넣지 않아요. 지연·복구 요구가 생기면 데이터 정합성과 운영 비용을 함께 검토해요. |
| 모든 상황의 무중단 보장 | 백엔드는 Kamal blue-green으로 전환하지만 호스트 장애와 호환되지 않는 스키마 변경까지 무중단을 보장하지 않아요. 모바일 앱의 스토어 배포와 백엔드 전환도 별개예요. |
| 마이크로서비스 분산 추적 | Flutter의 오류·분석 정보와 백엔드 로그·메트릭으로 현재 관측 범위를 구성해요. Jaeger·Zipkin 같은 분산 추적 체계를 기본으로 추가하지 않아요. |
| 모든 자원의 IaC 관리 | 반복 작업은 자동화하되, 계정 개설·권한 승인·스토어 설정까지 모두 Terraform·Ansible로 관리하는 것을 기본 요구로 두지는 않아요. 자동화한 영역과 수동 책임을 문서에 구분해요. |
| 서비스 메시 | 현재 구성에 Istio·Linkerd 같은 서비스 간 제어 계층을 추가하지 않아요. |
| 카나리 배포를 기본 릴리스 체계로 도입 | 현재 모바일 내부 배포와 백엔드 blue-green을 사용해요. 점진 트래픽 분배·자동 판정 체계는 별도 요구가 있을 때 검토해요. blue-green 자체는 비목표에서 제외해요. |
| Kubernetes·Helm | 현재 백엔드 홈서버와 Kamal 배포를 기본으로 사용해요. 클러스터 관리가 필요한 요구가 생기면 다시 판단해요. |
| 팀 규모만을 가정한 브랜치·리뷰 절차 확대 | 필요한 검증·리뷰는 유지하되 사용하지 않는 승인 단계나 브랜치를 늘리지 않아요. 실제 환경과 릴리스 경로에 맞는 현재 워크플로를 따라요. |
| 모델·API 코드 생성 파이프라인의 기본 도입 | `freezed`·`json_serializable`·OpenAPI codegen을 기본 설계로 추가하지 않아요. 수동 작성과 CI 검증의 선택은 해당 ADR을 따라요. 이 설명을 모든 종류의 코드 생성 사용 금지로 확대하지 않아요. |

<a id="채택한-것-vs-거부한-것"></a>

### 채택한 구성과 기본 구조에서 제외한 것

**채택한 구성**은 다음과 같아요.

- 백엔드는 단일 JVM 애플리케이션, 프론트엔드는 필요한 기능을 조립한 Flutter 앱을 기본으로 해요.
- 공통 개선은 검토한 뒤 수동 cherry-pick으로 전파해요([ADR-001](./adr-001-template-cherry-pick.md)).
- 개발용 기본 구현으로 외부 연동 준비와 화면·로직 개발을 나눠 진행해요([ADR-006](./adr-006-debug-fallback.md)). 실제 발송·분석·인증이 필요한 기능은 해당 구현과 자격으로 검증해요.
- 관리형 연동과 직접 운영을 함께 사용하고, 각각의 비용과 책임을 비교해요.
- `BootStep`·`AppKit`처럼 조립에 필요한 계약을 작게 유지해요. 파일의 줄 수를 설계 기준으로 삼지는 않아요.
- 캐시·로딩 UX는 정책과 기본값을 제공하고, 앱의 요구에 맞춰 선택해요.

**기본 구조로 채택하지 않은 것**도 유지해요.

- Clean Architecture의 계층을 일괄 적용하는 구조([ADR-002](./adr-002-layered-modules.md))
- BLoC·GetX로의 상태 관리 교체, 서비스 로케이터와 두 번째 DI 체계([ADR-005](./adr-005-riverpod-mvvm.md))
- OpenAPI codegen 기반 클라이언트 생성([ADR-009](./adr-009-backend-contract.md))
- 앱별 마이크로서비스를 기본으로 나누는 백엔드 구조([Spring ADR-001](https://github.com/storkspear/template-spring/blob/main/docs/philosophy/adr-001-modular-monolith.md))

#### 현재 브랜치와 배포 범위

Flutter CI는 `main` push와 `main` 대상 PR을 검증하고 수동 실행을 지원해요. Android 릴리스는 `v*` 태그 경로에서 별도 검증을 거쳐 Play Internal로 배포해요. 앱의 dev·prod flavor를 Git 브랜치와 같은 개념으로 다루지는 않아요.

짝이 되는 Spring 백엔드는 `develop`의 CI 성공 후 dev로, `main`의 CI 성공 후 prod로 배포할 수 있어요. 각각의 배포 gate가 켜져 있어야 하며, 두 환경은 같은 홈서버에서 별도 서비스로 운영해요. Flutter의 단순한 브랜치 구성을 근거로 백엔드 dev 경로까지 없다고 설명하지 않아요.

<a id="관리형-서비스-선호"></a>

### 관리형 서비스와 직접 운영의 비교

관리형 서비스는 운영 작업을 줄일 수 있고, 직접 운영은 기존 장비와 공통 인프라를 활용할 수 있어요. **두 방식에 드는 시간·비용·복구 책임을 함께 비교해요**.

| 영역 | 현재 구성과 선택 | 운영 책임 |
|---|---|---|
| Flutter 크래시·분석 | Sentry·PostHog 연동, 미설정 시 개발용 기본 구현 | 실제 수집 여부, 이벤트·사용자 정보, 자격과 보존 설정 확인 |
| 푸시 | 백엔드는 FCM을 사용해요. Flutter는 `NotificationService` 계약과 개발용 기본 구현을 제공하며 실제 푸시 수신 구현은 파생 앱에서 연결해요 | 디바이스·앱 자격, 실제 알림 수신 확인 |
| 모바일 배포 | 현재 자동화는 Android Play Internal 경로를 제공해요. iOS TestFlight는 별도 배포 준비가 필요해요 | 서명 자격, 스토어 계정·승인, 릴리스 검증 |
| 백엔드 데이터베이스 | Supabase의 PostgreSQL | 스키마·권한·마이그레이션·복구 절차 확인 |
| 백엔드 호스트·스토리지 | Mac mini 홈서버와 NAS MinIO | 호스트·네트워크·용량·업데이트·백업 관리 |
| 백엔드 관측 | Prometheus·Loki·Grafana, 조건에 따라 Alertmanager | 수집·보존·대시보드와 알림 도착 확인 |
| 백엔드 배포 | GitHub Actions·GHCR·Kamal blue-green | 검증한 이미지 선택, 전환과 롤백 확인 |

이 표는 Flutter 앱과 함께 운영하는 백엔드까지 포함해요. 로컬 전용 앱은 백엔드와 그 운영 스택 없이 구성할 수 있어요. 백엔드를 사용하는 앱은 서버 운영의 부담까지 전체 비용에 포함해 판단해요.

#### 로컬 개발·기능 선택·자격 소유

로컬에서 화면과 로직을 검증하고, 외부 연동은 준비한 환경에서 확인해요. 개발용 폴백은 실제 서비스 연결이 성공했다는 증거가 아니므로 출시할 기능의 연동 결과를 따로 확인해요.

인증이 없는 앱은 `AuthKit`, 서버가 없는 앱은 `BackendApiKit`을 설치하지 않는 구성을 선택해요. recipe는 조합의 시작점이며 YAML만 바꾼다고 Dart 설치 코드·생성자·provider override·네이티브 설정이 자동으로 바뀌지는 않아요. 조립 방법은 [ADR-021](./adr-021-multi-recipe.md)과 [Recipes](../reference/recipes.md)를 따라요.

자격도 사용하는 계정·앱·환경이 소유하게 해요. Flutter의 서명·스토어·외부 SDK 설정은 파생 앱에서 준비하고 필요한 빌드·릴리스 경로에 전달해요. 서버의 비밀 자격을 모바일 앱에 포함하지 않아요. 백엔드의 공유 SSH·Cloudflare·GHCR·Tailscale 값은 `.env.infra`, 환경별 값은 `.env.dev`·`.env.prod`가 관리해요. dev 초기화를 prod 초기화에 의존시키지 않는 원칙은 [Spring ADR-007](https://github.com/storkspear/template-spring/blob/main/docs/philosophy/adr-007-solo-friendly-operations.md)에 있어요.

### 시간 예산 원칙

기존 시간 예산은 설계와 자동화를 재검토하는 목표로 유지해요. 이미 달성한 실적이나 사용자에게 약속하는 처리 시간이 아니에요.

| 항목 | 목표 | 판단 범위 |
|---|---|---|
| 신규 앱 출시 준비 | 1일 이내 | 이름·설정 변경과 첫 배포 준비. 필요한 계정·자격·도구가 준비된 상태를 기준으로 해요. |
| 주당 운영 부담 | 4시간 이내 | 운영 중인 앱의 크래시 확인·문의와 리뷰 대응·업데이트를 합쳐 점검해요. |
| 월간 장애 대응 | 월 1회, 건당 1시간 이내 | 발생 빈도와 복구에 든 시간을 기록하고 반복 원인을 검토해요. |
| 문서로 온보딩 | 2시간 안에 첫 배포 | 필요한 계정·자격을 가진 새 작업자가 설명을 따라 설정하고 배포하는 과정을 기준으로 해요. |

스토어 심사나 외부 승인 대기는 작업 시간과 구분해 기록해요. 목표를 초과하면 반복 수작업, 기능 범위, 도구 선택과 문서를 다시 검토해요. 목표가 맞지 않게 된 경우에도 수치를 조용히 바꾸지 않고 이유를 남겨요.

### 설계 선택 포인트

**포인트 1 — 비목표를 ADR에 명시**
현재 제공하지 않는 기능·운영 체계와 그 이유를 남겨요. 이후 요구가 바뀌면 어떤 조건을 다시 검토해야 하는지 알 수 있어야 해요.

**포인트 2 — 나중의 확장만을 전제로 설계하지 않기**
현재 필요한 경계는 유지하되, 아직 없는 팀과 트래픽을 위해 운영 대상을 미리 늘리지는 않아요. 실제 요구가 생겼을 때 전환 비용과 효과를 비교해요.

**포인트 3 — 서비스 비용과 운영 시간 함께 비교**
월 요금뿐 아니라 직접 운영의 장비·저장 공간·업데이트·복구 시간을 함께 봐요. 기존 인프라를 재사용할 수 있는지, 외부 서비스가 줄여 주는 일이 무엇인지도 비교해요.

**포인트 4 — 필요한 품질을 구체적으로 정하기**
인증·데이터·결제의 정확성과 출시 검증을 유지하면서, 별도로 요구받지 않은 가용성 보증이나 배포 체계를 추가하지 않아요. 특정 가용성 수치를 모든 인디 앱에 충분한 값으로 일반화하지 않아요.

**포인트 5 — 지금 필요한 기능 선택**
앱에 필요한 Kit과 실제 구현을 설치하고 그 조합을 검증해요. 기능 선택은 화면만 숨기는 것으로 끝나지 않으며, 의존 Kit과 플랫폼 설정도 함께 맞춰요.

## 이 선택이 가져온 것

### 긍정적 결과

공통 계약과 조립 구조를 재사용하면서 앱에 필요한 기능을 고를 수 있어요. 새 기술을 검토할 때에도 도입 비용, 반복 작업, 복구 책임이라는 같은 기준으로 비교할 수 있어요.

시간 예산과 비목표를 적어 두면 운영 부담이 늘었을 때 무엇을 재검토할지 정하기 쉬워요. 출시 준비와 운영에 실제로 든 시간을 기록해 목표와 비교해요.

### 부정적 결과

수동 작성과 cherry-pick에는 사람이 변경을 확인하는 비용이 남아요. 앱 구성이 달라지면 설정과 설치 코드가 어긋날 수 있어 CI 검증도 유지해야 해요.

성장이나 팀 확대가 실제로 일어나면 모듈·배포·운영 체계를 다시 조정해야 할 수 있어요. 관리형 서비스의 가격·제약·장애와 직접 운영 인프라의 유지·복구 책임도 남아요. 두 방식을 함께 쓴다고 비용과 책임이 없어지는 것은 아니에요.

### 교훈 1 — 업계 표준은 조직 규모 가정이 전제

<a id="교훈-2--나중에-확장-가정은-대부분-실현-안-됨"></a>

### 교훈 2 — 나중의 확장은 확인된 요구에 따라 판단해요

앱 성장과 팀 확대를 미리 확정할 수는 없어요. 지금 필요한 기능을 만들고 변경 지점을 이해할 수 있게 유지해요. 확장 요구가 생겼을 때는 현재 구조를 고수하는 비용과 바꾸는 비용을 함께 비교해요.

<a id="교훈-3-관리형-서비스는-시간-vs-돈-비대칭-의-결과"></a>
<a id="교훈-3--관리형-서비스는-시간-vs-돈-비대칭-의-결과"></a>

### 교훈 3 — 관리형 서비스는 시간과 비용을 함께 비교해요

관리형은 운영 작업을 줄일 수 있고, 직접 운영은 기존 자원과 통제 범위를 활용할 수 있어요. 어느 쪽이 유리한지는 사용량, 자원, 운영자의 숙련도와 복구 요구에 따라 달라요. 가격이나 임의의 작업 시간 하나로 결론을 고정하지 않아요.

<a id="교훈-4-비목표-를-적어두면-완벽주의가-가벼워져요"></a>
<a id="교훈-4--비목표-를-적어두면-완벽주의가-가벼워져요"></a>

### 교훈 4 — 비목표를 적어두면 책임 범위가 분명해져요

현재 채택한 기능과 아직 보장하지 않는 수준을 구분해요. blue-green 배포를 쓰면서도 모든 상황의 무중단은 보장하지 않는다는 설명이 한 예예요. 같은 질문을 다시 검토할 때 이전 조건과 달라진 요구를 확인할 수 있어야 해요.
